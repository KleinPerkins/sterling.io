# S1-CORE-01 — owned Pet/Play interaction sessions

Status: accepted bounded nonvisual execution plan, effective only after this exact plan acceptance operation is explicitly consented and applied. Authorizes implementation, verification and normal App-owned PR delivery for the scope below. It does not accept the broader foundation drafts, production S1, UX/design, likeness, accessibility, S0 exit or release.

Prepared against `c3fac149f1dbf09719fba3e216178fb3aa6d8335`. Accepted PRD v1 remains frozen.

## 1. Proposed outcome

Deliver one reviewable, nonvisual PR that replaces anonymous Pet/Play start-stop mutation with a typed, generation-scoped interaction ingress owned by `SterlingCore` and used by the existing feasibility host.

After the PR:

- At most one Pet or Play interaction session is active.
- Every adapter input that can change interaction state carries a session token, globally monotonic generation, and source ordinal; adapter input cannot forge core-owned lifecycle or semantic terminal facts.
- A newer generation atomically terminates the prior generation before it can apply another effect.
- Duplicate, out-of-order, foreign-session, wrong-mode, and post-terminal inputs produce a typed ignored disposition and leave the entire `Simulation` value unchanged.
- Each accepted interaction step applies its elapsed-time/contact/play effects at most once. Each acquired session has exactly one accepted terminal result.
- Accepted Hide, Pause, Settle, Focus entry, replacing food transition, system suspension, care closure, mode change, lost capture, and natural Pet/Play boundaries terminate ownership with an explicit reason; a declined food offer does not.
- Presentation remains read-only. No renderer, animation, or audio callback can submit a gameplay-effect marker.

This is the smallest useful S1-CORE increment because it establishes the ownership/cancellation invariant needed by later affection, play, action-graph, and persistence work without implementing those systems.

## 4. Bounded typed contract

Names may be adjusted for Swift style during the governed preview, but the semantic fields and dispositions are part of this plan.

```swift
public struct CareSessionID: RawRepresentable, Codable, Equatable, Hashable, Sendable {
  public let rawValue: UInt64
  public init(rawValue: UInt64) { self.rawValue = rawValue }
}

public struct InteractionToken: Codable, Equatable, Hashable, Sendable {
  public let careSessionID: CareSessionID
  public let generation: UInt64       // process-local and globally monotonic
}

public struct InteractionStamp: Codable, Equatable, Hashable, Sendable {
  public let token: InteractionToken
  public let sourceOrdinal: UInt64    // 0 at begin; strictly increasing thereafter
}

public enum InteractionSource: String, Codable, Equatable, Sendable {
  case pointer, keyboard, accessibility
}

public enum InteractionSample: Codable, Equatable, Sendable {
  case pet(region: BodyRegion, quality: Double?)
  case play
}

// Only local acquisition/completion facts may arrive through InteractionInput.end.
public enum InteractionInputEndReason: String, Codable, Equatable, Sendable {
  case completed, cancelled, lostCapture, windowResignedKey, careClosed
  case modeChanged
}

// These are accepted facts produced by SterlingCore. They are not an ingress type.
public enum InteractionTerminalReason: Codable, Equatable, Sendable {
  case input(InteractionInputEndReason)
  case displayChanged, systemSuspended, hidden, paused, focusStarted
  case settledByOwner, supersededByFood, supersededGeneration
  case declined, policyUnavailable, naturalBoundary
}

public enum InteractionInput: Codable, Equatable, Sendable {
  case begin(stamp: InteractionStamp, mode: InteractionMode, source: InteractionSource)
  case step(
    stamp: InteractionStamp,
    elapsedSeconds: Double,
    sample: InteractionSample
  )
  case end(stamp: InteractionStamp, reason: InteractionInputEndReason)
}

public enum RuntimeLifecycleInput: String, Codable, Equatable, Sendable {
  case displayChanged, systemSuspended
}

public enum InteractionIgnoreReason: Codable, Equatable, Sendable {
  case invalidPayload
  case beginRequired(current: UInt64)
  case staleGeneration(current: UInt64)
  case foreignSession
  case duplicateOrOutOfOrder(lastAccepted: UInt64)
  case postTerminal(InteractionTerminalReason)
  case modeMismatch(expected: InteractionMode)
  case interactionTokenRequired
}

public enum RuntimeDisposition: Codable, Equatable, Sendable {
  case accepted
  case ignored(InteractionIgnoreReason)
}

public struct InteractionTerminal: Codable, Equatable, Sendable {
  public let token: InteractionToken
  public let finalOrdinal: UInt64
  public let reason: InteractionTerminalReason
}

// Returned by interaction, owner-control, lifecycle, ordinary advance, and reconciliation ingress.
public struct RuntimeResult: Codable, Equatable, Sendable {
  public let snapshot: SimulationSnapshot
  public let disposition: RuntimeDisposition
  public let runtimeSequence: UInt64?  // nil when ignored
  public let terminals: [InteractionTerminal] // bounded to at most two
}

public struct InteractionSessionSnapshot: Codable, Equatable, Sendable {
  public let token: InteractionToken
  public let mode: InteractionMode
  public let source: InteractionSource
  public let lastAcceptedOrdinal: UInt64
}
```

Required implementation details:

- `InteractionMode` and `BodyRegion` gain the conformances needed by the event/replay types; no tuning or geometry meaning changes.
- Generation and ordinal allocation use checked increment. Never use wrapping `&+=`; exhaustion refuses new ownership safely.
- `SimulationSnapshot` exposes the active `InteractionSessionSnapshot?` and accepted runtime sequence. It exposes no mutable view/native object.
- `Simulation` keeps only the current session, highest accepted generation, accepted runtime sequence, and one last-terminal tombstone. No unbounded event-ID set is required: the global generation plus per-session ordinal high-water provides bounded deduplication for this one-session model.
- Begin uses ordinal zero. Step/end require a strictly greater ordinal. Ordinal gaps are allowed so a future adapter may coalesce samples; lower/equal ordinals are ignored.
- Validation/lookup precedence is stable and tested: (1) structural shape/range, including begin ordinal zero and step/end ordinal greater than zero; (2) a step/end generation above the accepted high-water returns `beginRequired` without consuming that generation; (3) a generation below the high-water returns `staleGeneration`; (4) the current generation paired with the wrong care-session ID returns `foreignSession`; (5) the known terminal token returns `postTerminal`; (6) a live token with a lower/equal ordinal returns `duplicateOrOutOfOrder`; (7) a valid live token carrying the wrong sample mode returns `modeMismatch`. Only a structurally valid ordinal-zero begin may introduce and consume a future generation.
- A newer valid begin generation atomically terminalizes any active older generation as core-owned `supersededGeneration`, then evaluates the new Pet/Play begin. A declined/unavailable begin consumes the generation and returns an accepted core-owned `declined`/`policyUnavailable` terminal so delayed events for it can never activate later. One accepted begin may therefore report at most two terminals in its transient result; only the latest terminal is retained as the bounded tombstone.
- `elapsedSeconds` reuses the existing finite positive maximum-five-second reducer bound. Pet quality must be nil or finite in `[0, 1]`. All validation occurs before any state, sequence, time, notice, or RNG mutation.
- An accepted `step` applies the existing Pet or Play reducer once. If that step reaches the existing natural boundary, it records `naturalBoundary` and clears ownership in the same reduction.
- An ignored input is observational only through its returned disposition. It does not alter `Simulation`, including diagnostics inside the domain value.
- Every ingress method returns `RuntimeResult`; a nil-active snapshot alone is never an instruction to clear host ownership. The host clears only a currently held token that exactly equals one of the result's terminal tokens.
- `InteractionInput.end` accepts only `InteractionInputEndReason`. Owner/lifecycle commands, environment invalidation, supersession, begin refusal, and natural boundaries are evaluated and mapped to `InteractionTerminalReason` inside the core; an adapter cannot submit those terminal facts.

## 5. Ordering, cancellation, and effect rules

The PR deliberately does not build the full production event bus or drain scheduler. It establishes one serialized ingress seam and the interaction-specific invariants below.

1. The existing `AppDelegate.pendingOperation` chain remains the source-order bridge. All ordinary host mutations that can overlap care input route through it; no normal-path direct `runtime.send` may bypass the chain.
2. `SimulationRuntime` remains the only actor mutating `Simulation`. It assigns `runtimeSequence` only after an input validates and is accepted. Interaction, owner-control, lifecycle, ordinary advance, and reconciliation calls all return `RuntimeResult`.
3. Already accepted earlier input is not retroactively reordered. For a potentially preempting owner command, the core first validates/evaluates whether that command will take effect, then terminalizes active ownership and applies the command in the same accepted reduction. A declined Basic-food offer leaves Pet/Play ownership and effects active and returns no terminal token; the adapter cannot pre-submit `supersededByFood`.
4. An accepted Hide or Pause maps to core-owned `hidden`/`paused`; accepted Settle to `settledByOwner`; Focus-on to `focusStarted`; an accepted food transition that actually replaces care to `supersededByFood`; display invalidation and reconciliation/suspension to `displayChanged`/`systemSuspended`. Quiet, reduced-motion changes, and declined food do not terminate deliberate manual care.
5. Interaction ingress may report only local `completed`, `cancelled`, `lostCapture`, `windowResignedKey`, `careClosed`, or `modeChanged`. Display/Space invalidation and system suspension use their separate runtime lifecycle/environment ingress and are mapped by core. Repeated local cancellation after ownership is cleared emits nothing.
6. A higher-generation begin is a safe atomic fallback if its explicit predecessor terminal is delayed: old generation terminalizes once; the late old terminal is ignored. A higher-generation step/end without a begin is ignored as `beginRequired`, consumes no generation, and cannot supersede the active token. This makes correctness independent of Task cancellation without allowing non-begin input to manufacture ownership.
7. `AppDelegate`'s timer is the **only** effect-bearing step producer. `CareMat` reports local acquisition/end and updates latest region/quality data; it never emits a step. Each timer firing submits either one tokenized step or one ordinary advance, never both. While an interaction is active, anonymous advance returns `ignored(.interactionTokenRequired)` in its `RuntimeResult` without mutation.
8. The host never clears a token because a snapshot has `interaction == nil`. It examines `RuntimeResult.terminals` and clears only when a terminal's token exactly equals its currently held token. A result for N therefore cannot clear already allocated N+1.
9. Accepted Pet/Play steps are the only effects in this slice. Catch, bite, familiarity, preference, attention, object, behavior-marker, and persistence ledgers are not added. Later discrete markers must use their own semantic IDs and must not be accepted from rendering callbacks.

### Care-surface boundary preserved

The approved baseline makes the deliberately opened opaque care mat the owned interaction surface. Preserve that contract:

- A mouse-down originating outside the Care window/mat never acquires ownership when dragged through it.
- A mouse-down inside the care mat may acquire only the local `GestureInterpreter`. For pointer Pet, the host mints/submits the core token once, on the first valid body-region sample; a background-only down/drag/up creates no core session and changes no simulation state or notice. Dragging from mat background into a valid body region mints exactly one token at that transition. Pointer Play may mint on the owned mat down because the whole play mat is its valid region. Keyboard/accessibility Pet supplies its explicit virtual body-region sample when it begins.
- Pet effect remains body-region gated. `CareMat` only maintains latest region/quality data; `AppDelegate`'s timer samples that data and is the sole producer of at most one effect-bearing step per tick.
- Whether within-mat-background origin should remain allowed is a UX observation to record separately, not an automatic FZ-01 failure or a reason to add silhouette/global hit testing.
- No global event monitor, event injection, pointer movement, AX write, screen/document access, or external window inspection is introduced.
