# Sterling production-foundation architecture candidate

**Status:** Candidate for doc-warden preview; not an accepted decision, phase plan, design approval, S0 exit, likeness approval, accessibility acceptance, signing approval, or release authorization.  
**Observed source:** `KleinPerkins/sterling.io` at `8c59c4ed4d59781a1e1868f3ed87e6cab69740f0`.  
**Product authority:** `docs/reference/approved-product-specification-v1.md` (preserved approved planning baseline).  
**First proposed implementation body:** **FND-01 — bounded deterministic replay fixtures and attention-resume grace**.

## 1. Reading this candidate

This document distinguishes four kinds of statement:

- **Inherited** — restates an accepted requirement or boundary from the approved specification or `AGENTS.md`; it does not change that source.
- **Observed** — describes the current S0 code at the source revision above.
- **Proposal** — a new production-foundation choice that requires governed review before it becomes authoritative.
- **Gate** — a founder, feasibility, art, accessibility, distribution, or release decision that remains open.

The proposal preserves the baseline’s confirmed boundaries and tracks its proposed scope:

- One simulation owner; one cat remains the proposed launch default.
- Passive visuals ignore input; only a deliberately opened local care surface owns gestures.
- Rendering, animation callbacks, and audio completion never award gameplay effects.
- Hide, Pause, Focus, Quiet, Quit, and explicit recovery have precedence over autonomous behavior.
- Absence creates no hunger debt, relationship loss, queued invitations, or missed-event replay.
- No global event monitor, input injection, screen/document capture, real-file mutation, AX write, account, required network service, or frame-by-frame language model.
- Temporary geometric art is not Sterling's likeness. Nothing here invents his appearance, history, voice, or real temperament.

## 3. Runtime topology and trust boundaries

```text
@MainActor AppShell
  ├─ menu / SwiftUI care / SwiftUI settings
  ├─ passive OverlayHost + explicit CareHost
  ├─ EnvironmentAdapter (display and app-owned geometry only at base)
  ├─ FrameScheduler → CharacterPresenter → SKRenderer/Metal
  ├─ AudioPresenter
  ├─ PersistenceWorker
  └─ UpdateCoordinator (distribution builds only)
                   │ typed commands, sanitized samples, immutable snapshots
                   ▼
             actor SterlingRuntime
  ├─ clocks and input ordering
  ├─ simulation reducer and bounded state
  ├─ control/interaction arbiter
  ├─ behavior selector and action graph
  ├─ world generation and motion intent
  ├─ attention/learning/food ledgers
  └─ semantic event and save intent output
```

### 3.1 Ownership rules

1. **Inherited:** Only the runtime mutates character state, budgets, ledgers, behavior phase, reservations, and semantic history.
2. **Proposal:** AppKit/SwiftUI, render, audio, storage, geometry, and update adapters are clients. They may report facts or failures but cannot directly mutate domain state.
3. **Proposal:** The runtime never synchronously waits for the main actor, disk, GPU, audio device, optional desktop provider, or updater.
4. **Proposal:** Every adapter input carries a source-local ordinal; the runtime assigns the authoritative sequence when accepting it.
5. **Inherited:** A semantic marker is scheduled by the action graph. A presented frame or audio callback may report lag, but cannot create a bite, familiarity credit, catch, contact credit, or behavior completion.
6. **Proposal:** Production snapshots contain semantic codes and structured values. Human-facing copy is rendered at the UI boundary. FND-01 retains current S0 `notice` strings to avoid unrelated product-copy churn.

### 3.2 Concurrency contract

- `AppShell`, windows, focus, SwiftUI models, SpriteKit nodes, and Metal view operations are `@MainActor`.
- `SterlingRuntime` is one actor. Each accepted input is handled atomically; it does not expose mutable state.
- Persistence, content validation, optional geometry discovery, and atlas preloading execute outside the runtime and return bounded typed results.
- The presenter consumes immutable snapshots through a latest-value channel. Intermediate presentation snapshots may be coalesced; owner controls, terminal gesture results, semantic markers, and save intents may not be dropped.
- At most one character, one active care session, and one owned gesture exist. A care-session generation invalidates stale samples after cancellation or window loss.
- Cancellation is explicit and idempotent. Task cancellation alone is not a domain terminal result; the owner adapter must submit one terminal reason when it has acquired a session.

## 4. Lifecycle and time

### 4.1 Host lifecycle

The host lifecycle and owner policy are related but not collapsed into one enum.

| Host phase | Entry work | Permitted runtime work | Exit rule |
| --- | --- | --- | --- |
| `booting` | Create app shell, validate bundled content, load settings. | No autonomous selection or rendering. | Continue only with valid base content. |
| `restoring` | Load/migrate semantic save or choose an explicit recovery path. | Reconcile, validate IDs, establish home support. | Publish the first coherent snapshot once. |
| `ready` | Passive presence may render; care may open. | Normal policy-dependent simulation. | Owner control or system event. |
| `systemSuspended` | Cancel gesture, save if possible, stop frame/audio/integration sampling. | No active or availability time. | Wake/session activation performs one bounded return reconciliation. |
| `recovering` | Rebuild world generation and safe home intent. | Safety recovery only; no bid or autonomous switch. | Valid support and coherent snapshot. |
| `terminating` | Refuse new care, cancel ownership, request final save with a bounded deadline. | No new autonomous behavior. | Windows/audio/updater stop; previous valid save is never destroyed. |

Owner policy remains a value with at least `hidden`, `paused`, `quiet`, `focused`, effective reduced motion, and permitted-display state. Precedence is:

1. Quit/termination.
2. Hide or Pause.
3. Focus/Quiet restrictions.
4. Environment invalidation/recovery.
5. Direct care interaction.
6. Committed valid behavior.
7. Autonomous choice.

Hide and Pause freeze ordinary needs and learning. Quiet and Focus continue ordinary needs but suspend attention availability; Quiet also mutes immediately, and Focus favors home/rest. Clearing a restriction never replays work accumulated while it was active.

### 4.2 Four clock domains

| Domain | Advances when | Use | Never used for |
| --- | --- | --- | --- |
| Simulation active time | Runtime is ready, visible, and not hidden/paused/system-suspended. | Needs, recovery, action phases, cooldowns defined in active time. | Wall-clock absence or rendered animation. |
| Availability time | Active time plus owner availability; false during Quiet, Focus, lock, sleep, hide, pause, and unavailable sessions. | Rolling attention tokens and unanswered cooldown. | Needs or familiarity timestamps. |
| Wall time | Read only at durable checkpoint and return. | Bounded absence bucket and future local routine hints. | Running timers, reward reset, event ordering. |
| Presentation time | Local renderer/display-link time. | Pose interpolation, frame pacing, fades. | Any semantic effect or replay decision. |

**Proposal:** Use an injected host clock to produce bounded deltas; store durations rather than platform clock instants. Apple's `ContinuousClock` advances through system sleep, while `SuspendingClock` stops during sleep. Sterling should therefore use a suspending monotonic source for in-process active deltas, explicitly stop it on lifecycle suspension, and use wall time only for the approved bounded return algorithm. `ContinuousClock` remains suitable for performance measurement, not care debt. [Apple: ContinuousClock](https://developer.apple.com/documentation/swift/continuousclock), [Apple: SuspendingClock](https://developer.apple.com/documentation/swift/suspendingclock)

The runtime rejects negative/non-finite deltas. A host stall may advance at most the runtime's documented catch-up budget; anything larger becomes a typed `staleTick` requiring recovery or return reconciliation. It is never silently treated as hundreds of visible animation frames.

### 4.3 Availability transition invariant

**Inherited behavior with proposed timing:** whenever attention changes from unavailable to available, begin a return grace; the current prototype uses the specification’s proposed 60 seconds. A restart or toggle cannot buy tokens or immediately emit a queued bid.

**Observed defect:** `Simulation.send(.setQuiet(false))` and `Simulation.send(.setFocus(false))` do not call `AttentionBudget.resumeGrace()`. Grace currently occurs on Resume, Unpause, and return reconciliation only.

**FND-01 contract:** centralize comparison of `policy.allowsAttention` before and after every command, including Resume/Unpause, and remove their unconditional grace refresh. Call `resumeGrace()` exactly once on `false → true`, including the final release of nested Quiet + Focus. Repeating an already-effective setting must not extend the grace.

## 5. Commands, receipts, snapshots, and event order

### 5.1 Production command shape

```swift
struct CommandEnvelope<Payload: Sendable>: Sendable {
  let schemaVersion: UInt16
  let commandID: CommandID
  let requestedAtActive: Duration
  let careSessionID: CareSessionID?
  let expectedPolicyGeneration: UInt64?
  let payload: Payload
}

enum OwnerCommand: Sendable {
  case showSterling(destination: HomeDestination?)
  case settle
  case hide
  case resume
  case pause
  case unpause
  case setQuiet(Bool)
  case setFocus(Bool)
  case setAccessibility(AccessibilityPreferences)
  case beginCare(CareMode)
  case endCare(CareSessionID, CareEndReason)
  case offerFood(FoodOffer)
  case editObject(ObjectEdit)
  case reset(ResetScope, confirmation: ResetConfirmation)
}

enum CommandDisposition: Sendable {
  case accepted(sequence: UInt64, snapshotRevision: UInt64)
  case duplicate(originalSequence: UInt64)
  case rejected(CommandRejection)
}
```

**Proposal:** The command ID deduplication window is bounded and persisted only for effects that must survive restart, such as portion/bite and object-edit commits. An owner control acknowledged as accepted cannot be overwritten by an autonomous decision.

### 5.2 Interaction contract

An explicit care session owns a visible rectangular region, a mode, a generation, and at most one gesture. Passive presentation has no path into this API.

```swift
enum InteractionInput: Sendable {
  case begin(GestureID, point: LocalPoint, region: BodyRegion, source: InputSource)
  case sample(GestureID, delta: Duration, point: LocalPoint, quality: ContactQuality)
  case toyAnchor(GestureID, point: LocalPoint, features: PatternFeatures)
  case end(GestureID, GestureEndReason)
}

enum GestureEndReason: Sendable {
  case completed, cancelled, lostCapture, windowResignedKey
  case careClosed, displayLost, hidden, paused, modeChanged
}
```

Exactly one terminal result is accepted for an acquired gesture; repeats are idempotent. Samples with the wrong session/generation/gesture, non-monotonic delta, impossible discontinuity, or post-terminal sequence are ignored with a diagnostic reason and no punitive character interpretation.

### 5.3 Snapshot contract

Production presentation consumes a `RuntimeSnapshot` containing:

- `schemaVersion`, `snapshotRevision`, `simulationTick`, `acceptedSequence`, `policyGeneration`, and `worldGeneration`.
- Immutable character state needed for presentation, current behavior instance/phase, semantic presentation intent, support/motion intent, care-session state, effective policy, and power/render policy.
- Structured owner-response and recovery reason codes.
- No mutable renderer nodes, native windows, AX elements, external window IDs, arbitrary pointer trail, or persistence implementation object.

Snapshots are `Sendable`, immutable, and self-consistent. A newer policy generation always wins. Presentation may drop an older snapshot but cannot reorder snapshots or synthesize a missing semantic phase.

### 5.4 Ordering and cancellation

At each logical drain boundary the runtime processes:

1. lifecycle and owner-control inputs;
2. environment/capability invalidations;
3. interaction begins/samples/terminal results;
4. scheduled action-graph markers;
5. autonomous selection.

Within a class, runtime acceptance sequence is authoritative. Environment invalidation cancels dependent routes before another motion step. A direct interaction gets a semantic acknowledgment promptly but may wait for a planted exit (target ≤500 ms) or valid landing (target ≤800 ms). An interrupted meal commits only already accepted bite ordinals. Audio and renderer work is cancelled after, not before, the runtime publishes the new effective policy.

### 5.5 Recovery

Recovery is a runtime action, not a renderer trick. It records the invalidation reason, cancels dependent reservations and gestures, selects a valid nearby landing when one exists, otherwise issues the approved tuck/fade-to-home intent. Reduced motion replaces travel with the shortest readable state change. Recovery cannot grant curiosity, comfort, food, familiarity, play success, or attention credit.

## 6. Behavior and navigation contracts

### 6.1 One arbiter

The production runtime has one arbiter for owner policy, direct interaction, food, play, contact, navigation, attention, and autonomous behavior. There is no independent UI behavior controller or presentation state machine that can choose a conflicting activity.

Autonomous selection uses the scaffold’s proposed hybrid:

1. Generate candidates from character state, immutable world, content definitions, and committed intent.
2. Apply hard eligibility for policy, capability, route, support freshness, cooldown, attention, input ownership, reduced motion/jumping, and safe exit.
3. Score eligible candidates with the versioned proposed utility profile and stable candidate ordering.
4. Draw once from the seeded stream when a tie/softmax choice is required.
5. Commit an action graph with explicit approach, preparation, execution, recovery, completion, and safe-exit markers.
6. Retain the committed action unless invalid, directly preempted, or exceeded by the versioned proposed hysteresis rule.

Every selection records definition ID, instance ID, target IDs, score breakdown, rejected reasons, random checkpoint, world generation, and tuning/content identity. These records are diagnostic/replay semantics, not analytics.

### 6.2 Navigation geometry

Canonical simulation geometry is display-local logical points with lower-left origin. Pixels appear only at the view/render boundary.

```swift
struct WorldSnapshot: Sendable {
  let generation: UInt64
  let displays: [DisplayID: DisplaySpace]
  let surfaces: [SurfaceID: SupportSurface]
  let connections: [ConnectionID: RouteConnection]
  let objects: [ObjectID: HabitatObject]
  let exclusions: [ExclusionRegion]
  let home: HomeAnchor
}

struct MotionPlan: Sendable {
  let planID: MotionPlanID
  let worldGeneration: UInt64
  let supportReservation: Reservation
  let segments: [AuthoredMotionSegment]
  let safeExitMarkers: [MotionMarker]
  let landingEnvelope: Polygon
}
```

- A route is invalid if its world generation is stale, support expired/unknown, clearance fails, landing cannot be reserved, reduced-motion alternative is missing, or display is unavailable.
- Validate at planning, takeoff, and every motion step. An app-owned reservation blocks Sterling's object edits but cannot freeze another app.
- `NSScreen.visibleFrame` is dynamic and should not be cached as permanent habitat. Apple recommends view conversion APIs rather than applying one global scale factor. [Apple: NSScreen](https://developer.apple.com/documentation/appkit/nsscreen), [Apple: visibleFrame](https://developer.apple.com/documentation/appkit/nsscreen/visibleframe), [Apple: backingScaleFactor](https://developer.apple.com/documentation/appkit/nsscreen/backingscalefactor)
- Display reconfiguration is an invalidation signal, not an incremental promise. AppKit posts `didChangeScreenParametersNotification` when attached-display configuration changes. [Apple: display-configuration notification](https://developer.apple.com/documentation/appkit/nsapplication/didchangescreenparametersnotification)
- Runtime external tokens are never persisted. Persistence stores normalized app-owned layout hints and revalidates on launch.
- Spaces/full-screen window collection behaviors describe system window-management preferences, but they do not prove the desired one-cat experience across macOS configurations. FZ-02 remains required. [Apple: NSWindow.CollectionBehavior](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct)

## 7. Presentation, animation, audio, and content

### 7.1 Presentation boundary

Character presentation maps semantic intent to clips, additive channels, transforms, occlusion, and sound cues. It owns interpolation and frame pacing, not decisions. The proposed renderer remains `SKRenderer` over a controlled Metal host so scene updates are explicit and independent of app activation. The production presenter receives immutable snapshots and returns diagnostics only.

Frame policy follows the approved hypotheses:

- up to 60 Hz during direct active motion;
- 30 Hz ordinary walking;
- 12 Hz quiet breathing, or 6 Hz in Low Power Mode;
- zero frames while hidden/paused;
- coarsened simulation and zero animation when fully obscured;
- at serious thermal pressure prefer low-rate rest; at critical pressure stop optional work.

Apple exposes Low Power Mode and thermal-state notifications specifically so apps can reduce optional activity, display updates, and animation. [Apple: Low Power Mode](https://developer.apple.com/documentation/foundation/processinfo/islowpowermodeenabled), [Apple: responding to power and thermal notifications](https://developer.apple.com/documentation/xcode/responding-to-power-notifications)

### 7.2 Offline layered 2.5D pipeline

**Proposal, gated by D-01 and D-05:**

1. Founder supplies/approves reference material and explicit trait exceptions.
2. Art creates an approved model sheet: proportions, markings, asymmetry, palette, lighting, desktop-scale silhouettes, and allowed facings. This is the likeness gate; code does not guess missing facts.
3. Build a coherent offline reference rig and author root motion, contact, sockets, and common poses.
4. Render fixed camera/facing base clips to lossless sRGB alpha sources.
5. Export independent eyes, ears, tail, breathing/contact channels, masks, sockets, region maps, and markers where the approved shot supports them.
6. Validate manifests and source checksums before atlas packing.
7. Build family-scoped atlases; preload current family plus likely exit clips, then release strong references when no longer needed.
8. Validate clips at 80, 160, and 240 logical points against light, dark, and visually busy desktop fixtures before expanding the inventory.

Apple documents that SpriteKit atlases can reduce draw calls, that loading/decoding is expensive, and that atlas texture memory remains resident while referenced. That supports family-scoped preloading but does not settle atlas size; FZ-04 must measure it. [Apple: SKTextureAtlas](https://developer.apple.com/documentation/spritekit/sktextureatlas), [Apple: texture performance](https://developer.apple.com/documentation/spritekit/maximizing-texture-performance), [Apple: SKTexture lifetime](https://developer.apple.com/documentation/spritekit/sktexture)

### 7.3 Character pack and clip manifest

```text
CharacterPackManifest v1
  schemaVersion, packID, characterID
  likenessApprovalID?                 # absent means non-likeness fixture only
  rigVersion, modelSheetVersion, contentVersion
  sourceChecksums[], licenseProvenance[]
  colorProfile, logicalBodyLength, supportedFacings[]
  clips[], regionMaps[], atlasPages[], audioCues[]
  buildToolVersion, packChecksum

AnimationClipManifest v1
  clipID, clipVersion, rigVersion
  duration, loopMode, authoredFacing
  entryPose, exitPose, compatiblePredecessors[]
  rootDisplacement, plantedContacts[]
  semanticMarkers[] { id, ordinal, time, effectEligibility }
  safeExitMarkers[], sockets[], bodyRegionMapID
  occlusionMasks[], additiveChannels[]
  reducedMotionAlternativeID
  behaviorTags[], atlasReferences[]
```

Validation fails the build for missing/duplicate IDs, checksum mismatch, invalid duration, non-monotonic or duplicate marker ordinals, semantic marker after duration, absent safe exit, incompatible rig/pose, missing region/socket, unsupported facing, absent reduced-motion alternative where required, or atlas bounds outside the declared page.

`effectEligibility` is descriptive input to content validation; the runtime action graph still owns whether an effect commits. A renderer callback never commits it.

### 7.4 Contact, animation, and audio

- Body-region polygons are clip/facing-local and transform with the authored pose. Hit testing occurs only inside the care surface.
- Root motion and planted contacts come from the motion plan. Presentation conforms the clip; it does not move the semantic character independently.
- Incompatible silhouettes use a shared pose or dedicated transition, never an arbitrary whole-body crossfade.
- Reduced motion removes long travel, repeated wiggle, large leap, and vigorous shake while preserving gaze, blink, breath, acceptance, and withdrawal.
- Audio cues are local presentation intents with category, variation group, priority, fade, and policy generation. Quiet/Focus/Hide/Pause cancel or fade them immediately.
- One vocal foreground cue, one purr bed, and one movement/toy cue is the proposed mixer bound. Every consequential cue has a visual equivalent.
- `AVAudioPlayerNode.stop()` clears scheduled buffers, which is useful for policy preemption; completion callbacks remain presentation facts only. [Apple: AVAudioPlayerNode](https://developer.apple.com/documentation/avfaudio/avaudioplayernode)

## 8. Persistence, migration, diagnostics, and updates

### 8.1 Persistence

**Proposal:** Store one versioned semantic `SaveEnvelope` under the platform-resolved Application Support directory, with atomic primary replacement, previous-good generation, checksum, and a small recovery metadata file. Apple's Application Support URL resolves inside a sandbox container for sandboxed apps and under the user's Library otherwise, so the implementation must use the API rather than a hard-coded path. [Apple: Application Support directory](https://developer.apple.com/documentation/foundation/url/applicationsupportdirectory), [Apple: file-system guidance](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively)

Persist:

- schema/content/tuning/app/random-algorithm identities and revision;
- relative clock/budget/learning durations and a wall checkpoint;
- bounded character state, preferences, app-owned habitat, history, food ledger, and coherent resume intent;
- simple user settings needed before runtime restore.

Never persist:

- platform clock instants, renderer nodes, clip stack, in-progress gesture, native windows/views, AX references, external window/Space IDs, raw pointer trails, app titles, URLs, screenshots, or audio capture;
- transient presentation notice copy as domain history.

Save after a committed meal/object/reset/learning change, on Hide/Quit/suspension, and on a debounced dirty interval. Do not write per frame or per gesture sample. A save failure retains the last good generation, reports one calm typed notice, retries with bounded backoff, and never blocks Quit beyond the reviewed deadline.

### 8.2 Migration and recovery

- Migrations are explicit `vN → vN+1`, pure where possible, fixture-backed, and produce a receipt of repairs/defaults.
- Decode into untrusted wire types, validate bounds and IDs, migrate, then construct runtime types. Do not rely on `normalize()` silently converting corrupt/non-finite data into a valid emotional state.
- Future schema is read-only recovery: do not overwrite it.
- Corrupt primary falls back to previous-good. If both fail, preserve them and offer an explicit new-memory start.
- Unknown content maps only through a reviewed compatibility table; otherwise recover to Basic/home without fabricating a preference.
- Resume revalidates semantic intent. Never resume airborne motion, owned input, or external support.

### 8.3 Diagnostics and privacy

Release diagnostics are local, bounded, and off by default beyond the ordinary semantic history needed for continuity. The opt-in inspector may show activity/phase, top candidate scores and rejection reasons, budgets, reservations, render policy, save status, and recent semantic events.

Export requires an explicit owner action and contains only synthetic/app-owned geometry, interaction-local coordinates when necessary, version identities, sanitized commands/events, and aggregate timings. No external app identity/content, screen pixels, global pointer trail, typed content, meeting data, microphone/system audio, or autonomous upload.

### 8.4 Update boundary

- Local builds and probes never create/start the updater.
- Signed distribution builds may expose **Check for Updates…** and an explicit automatic-check preference. Automatic installation remains disabled.
- Update network activity is not a simulation dependency and never changes character state, attention, familiarity, habitat, or replay.
- An available update is AppShell state, not an attention bid and not character dialogue.
- Before owner-approved installation/termination, AppShell closes care, submits one terminal cancellation, requests a bounded save, stops audio/rendering, and then yields to the updater. Failure leaves the current app and previous valid save usable.
- Feed/signature/notarization/release validation remains governed by the existing release runbook. This candidate does not authorize a release or change protected updater/automation paths.

## 9. SwiftUI information architecture and access

### 9.1 Window model

**Proposal:** retain the AppKit application lifecycle and custom overlay panels. Host new SwiftUI care/settings/notebook content inside deliberate windows. This avoids making passive overlays SwiftUI scene authority while still using native controls and accessibility semantics.

- **Passive overlay:** borderless, non-key, non-main, mouse-transparent, excluded from accessibility traversal as a control surface.
- **Care window:** one summonable key-capable window; opening it is the explicit transition to local input ownership. It never requires a global monitor and never steals focus merely because Sterling is shown.
- **Settings:** native settings window, reachable from menu and care. SwiftUI's `Settings` scene can supply a standard Settings item/window, but integration with the retained AppKit lifecycle must be proven for the deployment target before adoption. [Apple: SwiftUI Settings](https://developer.apple.com/documentation/swiftui/settings)
- **Notebook:** secondary read-only/detail window or care destination; it reports bounded evidence, not judgments based on one refusal.
- **Diagnostics:** development/explicit opt-in only, separate from owner care.

### 9.2 Care information architecture

The compact care window has a stable top-level mode control:

1. **Pet** — visible interaction mat, receptive/boundary status, keyboard body-region choice, Done.
2. **Feed** — Basic and approved flavor/texture choices, one current bowl/portion, replace confirmation only if a bite is active.
3. **Play** — approved toy choices and an explicit local play mat; arrows affect the toy only while that surface has focus.
4. **Place** — app-owned nook/furniture/object placement, exclusions, safe removal and recovery.
5. **Notebook** — secondary observations with evidence threshold and tentative language.

Persistent control strip: current mode, Settle, Done; Hide/Pause/Focus/Quiet remain in the menu and can also appear as native labelled controls without impersonating character desires. No hunger meter, streak, urgency badge, or compulsory tutorial.

Care-window states:

| State | UI behavior | Runtime behavior |
| --- | --- | --- |
| `opening` | Show controls disabled briefly; no gesture surface yet. | Request/restore visibility and safe care destination. |
| `approaching` | Show readable progress/status and Cancel. | Valid route or explicit approved recovery; no acquired gesture. |
| `ready(mode)` | Enable that mode's controls and focus order. | Care session exists; no gesture until deliberate begin. |
| `interacting` | Keep mode stable; show local visual acknowledgment. | One owned gesture/action. |
| `boundary` | Preserve controls; make withdrawal understandable without blame. | End/decline through normal state rules. |
| `settling` | Disable new sample input; Done remains available. | Safe exit/settle. |
| `cancelled/recovering` | Release input immediately and explain the local cause. | Terminal cancellation, revalidate support, no effects from stale samples. |
| `suspended` | Window hides or becomes inert. | No time/input/audio/render work; bounded return later. |

### 9.3 Settings information architecture

### 9.4 Keyboard, VoiceOver, and reduced motion

- Standard Tab/Shift-Tab traverses native controls in a stable visual order. Space activates the focused control.
- Escape cancels the active local gesture and closes care in one action. It never acts on the underlying app.
- Arrow keys select head/back in keyboard Pet, and move the lure only when the Play surface is explicitly focused. They otherwise retain native navigation behavior.
- Every control has a concise label, value, hint when needed, enabled/disabled state, and equivalent command. Custom actions supplement rather than replace ordinary buttons.
- VoiceOver focus moves only for owner-requested care transitions, recoverable errors, or destructive reset confirmation—not for each animation or mood change. SwiftUI offers `AccessibilityFocusState`, but its use must be sparse and tested with VoiceOver. [Apple: AccessibilityFocusState](https://developer.apple.com/documentation/swiftui/accessibilityfocusstate)
- The owner can complete core care without pointer, sound, color alone, or large motion. Consequential audio always has a visual equivalent.
- Effective reduced motion is the safer union of the system preference and the user's Sterling preference; Sterling never overrides a system request for reduced motion. SwiftUI exposes the system value through `accessibilityReduceMotion`. [Apple: accessibilityReduceMotion](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion)
- Reduced motion preserves causal readability with eye/head cues, posture, brief fades at recovery boundaries, and explicit state text where necessary. It does not simply freeze the character.

These are contracts and test targets, not accessibility acceptance. VoiceOver, keyboard, contrast, scaling, motion, focus, and physical input still require real-device/manual evidence.

## 11. FND-01 — smallest independent production-foundation slice

### 11.1 Purpose and boundary

FND-01 gives the existing pure core a durable way to reproduce semantic scenarios and fixes one requirements-visible budget defect. It produces implementation evidence without choosing production UI, art, likeness, tuning, persistence location, package structure, or a full event bus.

Owned implementation scope:

- `Sources/SterlingCore/`: a small versioned replay record, validation, adapter, and synchronous runner over the existing `Simulation` reducer.
- `Tests/SterlingCoreTests/`: replay/validation fixtures and attention-grace regressions.
- Optional small synthetic fixture files under the ordinary test tree only if repository/source policy prefers files over builders.

Out of scope:

- SwiftUI/AppKit production UI, animation/content, likeness, behavior tuning, world/navigation, disk persistence, updater, package dependency changes, release/protected automation, or claims that S0/S1 passed.
- Generalizing the runner into the production command/event bus.
- Recording pointer trails, desktop/app data, wall-clock history, renderer frames, audio, or live user sessions.

### 11.2 Replay contract and validation

FND-01 is an intentionally small fixture adapter. Its exact implementation and acceptance scope are in the companion execution plan. The proposed types are `SimulationReplayIdentity` (code/content/tuning versions), `SimulationReplayRecord` (zero-based contiguous sequence and typed input), `SimulationReplayInput` (command, bounded elapsed/contact quality, or bounded-return reconciliation), and `SimulationReplay` (schema version, identity, seed and ordered records). The current `SeededRandom` algorithm remains SplitMix64 v1; changing it requires a new code/tuning identity and fixture review.

Replay starts from `Simulation(seed:)` and validates the entire envelope against the caller’s expected identity before any input executes. It never deserializes private runtime state or captures live input. Proposed fixture limits are 4 MiB encoded input, 10,000 records and eight hours of cumulative active input; each advance must be finite, positive and at most five seconds, quality must be finite in [0,1], and absence must be finite/nonnegative. These are engineering fixture bounds, not product requirements or absence limits. Out-of-order/duplicate/gapped sequences and unknown schema/identity fail rather than partially execute or migrate.

The Codable representation is versioned developer data, not a public wire or persisted save compatibility promise. A future public replay interchange requires an explicit strict field/tag schema and migration strategy. The runner calls only `Simulation.send`, `advance` and `reconcileReturn`; it returns the full `Simulation` for state/RNG equality. The exact step schedule is part of replay identity. Cross-version/platform floating-point identity is not promised.

The execution plan requires round-trip and direct-reducer equivalence, petting rise/end/re-entry, play fatigue/re-entry, hidden/paused freeze, forgiving absence and Quiet/Focus grace regressions, plus invalid identity/schema/sequence/time/quality/work-size rejection. Whole-envelope validation precedes execution; there is no externally mutable simulation reference and no disk or network effect. FND-01 adds no checkpoints, production event bus, new package or dependency. Future actor-assigned sequencing and durable effect deduplication remain separate S1/S2 work.

## 12. Current domain weaknesses and sequencing

| Observation at source revision | Risk | Smallest response |
| --- | --- | --- |
| `SimulationCommand` is neither a versioned wire type nor replayable; the only replay test manually repeats calls. | Fixtures can drift and cannot carry build/tuning identity or validation bounds. | **FND-01:** explicit replay adapter and runner. |
| Quiet/Focus clear without calling `AttentionBudget.resumeGrace()`. | Immediate bid can occur after a long available history despite the required 60-second grace. | **FND-01:** central false→true availability transition and regressions. |
| `advance(seconds:)` silently caps each call at five seconds. | Caller scheduling affects lost elapsed time and is not inspectable. | FND-01 rejects replay advances above five seconds; later runtime returns typed stale/clipped-time diagnostics. |
| `SimulationSnapshot` omits RNG, phase timers, attention budget, meal progress, and interaction counters. | Snapshot alone cannot prove deterministic continuation. | FND-01 final result compares full `Simulation`; later split durable state from presentation snapshot. |
| Runtime commands have no IDs, receipts, rejection reasons, or deduplication. | UI races and duplicate effect requests are hard to diagnose. | Later command-envelope slice; do not inflate FND-01. |
| Contact is an optional quality value smeared over an advance interval; gesture/session/generation and terminal reason are absent from core. | Stale samples and cancellation causes cannot be proven at the runtime boundary. | Later interaction-contract slice after replay foundation. |
| `unit(_:)` maps non-finite values to zero. | Safe for current arithmetic, unsafe as silent persistence-corruption policy. | Decode/validate/migrate wire values before constructing domain state in persistence slice. |
| `WorldRect.clamped` can return the inclusive max edge while `contains` excludes it. | A clamped point can fail a subsequent ownership test at the top/right edge. | Small geometry invariant test/fix in later input/geometry slice. |
| `DisplayGeometry.token` is Codable with persistent-looking state. | A transient runtime display token could be stored accidentally. | Separate runtime display identity from persisted normalized layout hints in world/persistence slice. |
| Current host serializes its own queued tasks, but the runtime assigns no global sequence across future lifecycle/environment/input producers. | Ordering correctness will weaken as adapters grow. | Later runtime-envelope slice with actor-assigned sequence. |
| `notice` is domain-owned English text. | Localization/accessibility copy changes can become semantic-state changes. | Later structured response codes; keep unchanged in FND-01. |
| Current persistence is in-memory and return uses a supplied wall duration without clock-corruption evidence. | Restart continuity/migration and conservative clock recovery are unproved. | Dedicated save/migration/clock slice after typed runtime state. |

Recommended sequencing after FND-01:

Follow the dependency-ordered packages in the execution plan: S0 evidence/art preparation alongside S1-CORE typed clocks, commands, interaction and cancellation; gated S1-CARE/S1-ILLUSION; S2 arbitration, care and persistence; S3 world/placement; S4 launch depth. Synthetic asset validation can proceed independently, while likeness and production UI gates stay open.

This sequence is a proposal, not a replacement phase plan. It does not reorder or close S0–S4 in the accepted roadmap.
